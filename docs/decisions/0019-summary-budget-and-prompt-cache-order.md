# 0019. Summary token budget and cache-stable prompt order

- Status: accepted
- Date: 2026-11-01

## Context
- **Summaries never finished.** Every summarisation call ended `finish=Length out=300`. Reproduced live on a synthetic conversation (contributor model, `minimal` effort, the shipped prompt): 188 of the 300 output tokens were reasoning, so the text stopped mid-sentence after 469 characters. Three causes: `max_output_tokens` includes reasoning (`meta-model-api.md` §1.4); the prompt asked for up to 1,200 characters (≈ 300 tokens on its own); and the model copied the previous summary verbatim. `Summarizer` then stored whatever text had arrived, so a cut-off reply silently dropped the facts it never reached. An empty reply (all budget spent on reasoning, as in the recorded `responses_incomplete` fixture) replaced the whole memory with an empty string.
- **Prompt caching.** Meta caches the longest matching token prefix automatically; there are no breakpoints, and everything after the first differing token is recomputed ([docs:prompt-caching]). `prompt_cache_key` is optional and only routes requests that share a prefix to the same backend; the docs ask for one key per use case, never per user or session. The context block (memory summary + scene, with ages such as "2 min ago") was the first input item, so it changed every turn and kept the whole conversation history out of the cache.

## Decision
- **Summary.** `MemoryLimits.SummaryOutputTokens` 300 → 1,024. The prompt asks for terse notes in short sentences, at most `SummaryChars / 8` words (150), and drops small talk, jokes and tool details. Live with the new prompt: 162 reasoning + 123 text tokens on a 1.6k-character input and 220 + 136 on a 4.3k-character input, all `completed`. `Summarizer.Run` returns null unless the reply finished with `Stop` and has text; `ConversationMemory` then keeps the old summary and items and logs `evt=memory.summary_rejected`. The fold is retried after the next turn, as for a provider failure.
- **Prompt order.** Input is recent items → context block → user turn (was context → recent → user). The request writer emits `prompt_cache_key`, `instructions` and `tools` before `input`, so the body bytes have the same prefix as the prompt. Instructions contain nothing per turn. An EditMode test asserts that turn 2's body starts with turn 1's body up to its context block.
- **Cache keys.** `jolly-voice` for voice turns and vision, `jolly-memory` for summarisation (`ResponsesChatOptions`). The parameter was accepted live (200, echoed in the response).
- **Persona prompts.** The tool paragraph that was copied into three personas in two locales is gone. "When to call" guidance lives in the tool descriptions, which are sent only for the tools a persona has, so Listener is no longer told to use `capture_and_identify`, which it does not have. Rules that hold for every persona are in `PromptBuilder`: one to three spoken sentences with the answer first, no stage directions (`*waves*` would be read aloud), no claims of seeing anything that was not just captured, one short sentence when a tool fails, and never asking for passwords, PINs or bank details.

## Consequences
- A summary that keeps failing leaves the recent items over their caps and costs one background call per turn until it succeeds. That is bounded by the budget meter, and nothing is lost.
- From the second turn, the cached prefix covers instructions, tools and all earlier turns. It resets when a summary folds items, which happens about once every eight turns.
- **Not yet measured.** Four synthetic two-turn calls (old and new order, no cache key, non-streaming) all reported `cached_tokens: 0`, including the shared instructions + tools prefix, so this run says nothing about the order. The earlier research run did see hits within a turn (625 of 772). speculation: the calls landed on different backends, which `prompt_cache_key` is meant to prevent. The device self-test logs `cached=` in every `evt=llm.completed` line, and that is where the next check belongs.
